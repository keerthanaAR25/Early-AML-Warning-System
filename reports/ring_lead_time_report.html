Operational definitions

  • observable_time: cycle: day of last (closing) edge; fan_in/fan_out: day the k-th distinct counterparty has transacted (k=observable_k), else last transaction day
  • warning_time: earliest day any transaction of the ring is flagged by the daily budget (out-of-sample days only)
  • lead_time: observable_day - warning_day, in days; >0 means warned before the ring became observable
  • evaluable_ring: ALL transactions of the ring fall inside the scored period (first_day >= first scored day) and its observable_day is scored; this avoids right-truncating warnings. The JSON also keeps summary_observable_in_period (only observable_day in the scored period), which is truncated for slow rings.

Caveats

  • AMLSim-specific shortcut: ring members are drawn from otherwise-dormant accounts, so 'first-ever sender' transactions are almost always ring transactions after a warm-up. xgb_without_novelty uses same-day information only (no account history); newness_rule is a two-bit rule (first-ever sender / first-ever receiver); random is a control. If xgb_with_novelty does not clearly beat newness_rule, the model adds nothing beyond the shortcut.
  • Labels are used only as training targets for rows before each scored block and for evaluation.
  • Rings that continue into a scored block are excluded from that block's training set (ring-grouped split).
  • Daily timestamps: a flag on the same day as observable_time gives lead 0 (not early).
  • Evaluable ring counts are small for some typologies; read N and the confidence intervals.
